# Setup: pnpm monorepo with React+Vite app and React+Vite library

This guide is tailored to your stack: **pnpm workspaces**, one app + one library, with progressive threshold tightening.

## 1. Install the packages

From your monorepo root:

```bash
# mutest goes at the workspace root because it's the orchestrator
pnpm add -Dw mutest

# Stryker peer-deps go in every package that has tests.
# -w would put them at the root, which works but bloats install graphs.
# Use --filter to add them to the specific packages instead:
pnpm --filter @my/web-app --filter @my/ui-lib add -D \
  @stryker-mutator/core \
  @stryker-mutator/vitest-runner \
  @stryker-mutator/typescript-checker
```

The `typescript-checker` is the single biggest perf win for TS — it skips mutants that won't even compile, so they never reach Vitest.

## 2. Add a config to each testable package

Copy `templates/library.mutest.config.json` into your library and `templates/app.mutest.config.json` into your app. They differ mainly in:

- **Library**: threshold 70/85 (break at 70, target 85). Excludes index re-exports, type files, test utils.
- **App**: threshold 55/70 (break at 60, target 70). Excludes `main.tsx`, route definitions, mocks. Routes and bootstrapping code aren't really mutation-testable.

```
your-repo/
├── pnpm-workspace.yaml
├── package.json
├── apps/
│   └── web-app/
│       ├── package.json
│       ├── vitest.config.ts        # your existing config
│       ├── mutest.config.json      # ← from app template
│       └── src/...
└── packages/
    └── ui-lib/
        ├── package.json
        ├── vitest.config.ts
        ├── mutest.config.json      # ← from library template
        └── src/...
```

## 3. Add scripts to root `package.json`

```json
{
  "scripts": {
    "test:mutation": "mutest",
    "test:mutation:lib": "mutest --filter ui-lib",
    "test:mutation:app": "mutest --filter web-app",
    "test:mutation:report": "mutest --report-only reports/mutation/mutation.json"
  }
}
```

`pnpm test:mutation` from the root will discover all packages, run mutation testing in each, and produce a per-package report plus a top-level aggregate.

## 4. Add `.gitignore` entries

```gitignore
# Generated by mutest / Stryker
.stryker-tmp/
reports/mutation/
stryker.log
```

## 5. Set up CI with the ratchet

Drop `templates/github-actions-mutation.yml` into `.github/workflows/mutation.yml`. The interesting bit is the `--threshold-apps 70 --threshold-libs 85` line — those are the *current* targets, not the destination.

**Ratchet schedule** (edit the numbers in the workflow as you progress):

| Phase | Apps | Libraries | Focus |
|---|---|---|---|
| Week 1-2 | 60% | 70% | Establish baseline. Look at the worst-scoring files and add assertions. |
| Week 3-4 | 70% | 80% | Tackle `NoCoverage` mutants — these are code paths no test touches. |
| Week 5-8 | 75% | 85% | Push branch coverage. Look at `EqualityOperator` and `ConditionalExpression` survivors. |
| Week 9-12 | 80% | 90% | Target boundary cases. `>` vs `>=` survivors mean you're missing edge values. |
| Week 13+ | 80% | 95%+ | Approach 99%. Beyond ~95% you'll need `excludedMutations` for genuinely equivalent mutants. |

Apps top out lower than libraries on purpose — UI integration code (routing, bootstrapping, third-party API plumbing) has equivalent mutants that aren't worth chasing. 80% on a React app is genuinely good.

## 6. First run

```bash
# From the monorepo root:
pnpm test:mutation
```

Expected first-run experience:

1. Per-package detection prints. You should see your library and app both detected, both classified correctly (library vs app).
2. Stryker runs in each package — this takes a while the first time (no incremental cache yet). For a library of ~3000 LOC, expect 5-15 minutes. For an app, 10-30 minutes.
3. You'll see a per-package efficacy report, then a top-level aggregate.
4. Open `packages/ui-lib/reports/mutation/mutation.html` in a browser — this is Stryker's interactive HTML report. Each file shows surviving mutants inline. Click a mutant to see the diff and the tests that ran against it.

## 7. Improving the score — practical playbook

Open the HTML report and look at survivors in this order:

**a. `NoCoverage` first.** These are mutants where no test touched the code at all. Often this is dead code you can delete, or a code path you didn't realize was reachable. Cheap, high-impact wins.

**b. `EqualityOperator` survivors.** `==` ↔ `!=`, `===` ↔ `!==`. These survive when your tests check the happy path but not the negative one. Add one assertion per survivor.

**c. `ConditionalExpression` survivors.** A conditional was forced to `true` or `false` and your tests didn't notice. Add a test that exercises the *other* branch.

**d. `BooleanLiteral` survivors.** `true` ↔ `false` on default props, return values, flags. Often means your assertion uses `toBeTruthy()` when you should use `toBe(true)`.

**e. `StringLiteral` survivors.** A string was replaced with `""`. Mostly noise for UI copy; in *business logic strings* (event names, action types, API endpoints) these matter — add specific assertions or add `StringLiteral` to `excludedMutations` for that file via Stryker's disable comments:

```ts
// Stryker disable next-line StringLiteral
const ANALYTICS_EVENT = 'user.signup.completed';
```

**f. `BlockStatement` survivors.** A whole function body was emptied. Means the function is called but its effect isn't asserted on. Common with side-effecting functions — add assertions on the side effect (mock calls, state changes, DOM changes via testing-library).

## 8. React-specific tips

- **`@testing-library/react`**: queries like `getByRole('button', { name: /save/i })` kill `StringLiteral` mutations on visible text. Switch from `getByTestId` where it makes sense.
- **`@testing-library/jest-dom`**: matchers like `.toBeDisabled()`, `.toHaveClass()`, `.toHaveAttribute()` kill many `BooleanLiteral` and `ConditionalExpression` mutants that simpler assertions miss.
- **`userEvent.click(...)` then asserting on outcomes** kills more mutants than `fireEvent` because it triggers the full event chain.
- **For hooks**, use `renderHook` from `@testing-library/react` and assert on the returned state across re-renders — this catches `useEffect`/`useMemo` dependency mutations.

## 9. Vite-specific tips

- Stryker copies your project to `.stryker-tmp/` and runs Vitest there. If your `vite.config.ts` does anything path-relative weird (`import.meta.url`-based, custom plugins reading from disk), Stryker will fail with cryptic errors. Test with `mutest --dry-run` and fix `vite.config.ts` first if needed.
- The Vitest runner forces `coverageAnalysis: "perTest"` automatically — leave this alone, it's what makes runs tractable.
- If your app has very slow tests, increase `timeoutMS` in `mutest.config.json` (default 60000). Stryker computes per-mutant timeout as `netTime * timeoutFactor + timeoutMS`, so the absolute timeout is forgiving but the *factor* matters for tests that already take 1+ seconds.

## 10. When you want to skip a file or a mutation

Three ways, from least to most invasive:

1. **Per-line / per-block disable comment in source**:
   ```ts
   // Stryker disable next-line BooleanLiteral
   const FEATURE_FLAG = true;
   ```
2. **Exclude a glob in `mutest.config.json`** under `mutate` — add a `!` pattern.
3. **Exclude a whole mutator** via `excludedMutations: ["StringLiteral"]`. Use this last; it removes that mutator everywhere in the package.

Don't blanket-exclude mutators to inflate your score. The point of the score is to expose weak tests; if you exclude survivors to hit 99%, you've inflated a number without improving anything. The threshold should reflect the genuine state of your tests.
